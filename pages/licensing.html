Licensing

Entitlement without holding sites hostage.

Distributed WordPress code is GPL-2.0-or-later. Commercial controls apply to the separately provided service and delivery — not to whether your site keeps working.

The licensing model

services/licensing-service is an independent entitlement, activation, signed-update, package-delivery, and portal service. It is deployed separately from WordPress.

i

The GPL line matters. The theme, plugin, and child starter are GPL-2.0-or-later. What is commercially controlled is access to the update service and package delivery — a distribution channel, not the code you already have.

If the service is unreachable

✓

Sites keep rendering. WordPress continues serving from installed code if the licensing service is unavailable. Signed entitlement caches provide a bounded administrative grace state rather than an immediate hard stop.

This is a deliberate design property. An outage in your licensing infrastructure should never take a client's public website down.

Signed updates

Update manifests are signed with an Ed25519 key. The WordPress client verifies the signature before trusting a manifest, so a compromised or spoofed update endpoint cannot push arbitrary code into a site.

Key rotation is a trust-set operation, in this order:

  1. Generate offlineCreate the new Ed25519 signing key in the controlled release environment.
  2. Publish the public key firstAdd it to WordPress packages as a trust-set entry before using the new private key.
  3. Verify adoptionDeploy the trust-set release and confirm sites have it.
  4. Switch signing keysOnly now start signing with the new private key.
  5. Retain the old verification keyThrough the maximum entitlement-cache, update-manifest, and rollback window.
  6. Revoke and recordRetire the prior key and log the rotation in the operator audit log.
!

Never place a signing private key in WordPress or a public web root. Rotate license peppers through a versioned multi-pepper verifier — replacing the only pepper without rehashing customer keys during successful validation will invalidate them.

Package grants

Download grants expire after five minutes and are bound to product, version, license, and site. A leaked grant URL is therefore short-lived and not portable to another site.

Webhook signatures allow five minutes of clock skew, and event IDs are persisted so a replayed webhook cannot cause duplicate side effects.

Deploying the service

Deploy independently from WordPress, behind TLS, a reverse proxy, and managed network controls. Use a long-running Node 24 runtime. Package binaries belong in immutable object storage or a read-only mounted release directory.

Production startup fails closed when any of these is missing:

LICENSE_KEY_PEPPER
DOWNLOAD_GRANT_SECRET
MANIFEST_PRIVATE_KEY_PEM
OPERATOR_TOKEN
PUBLIC_ORIGIN
PACKAGE_ROOT

Set NODE_ENV=production. Also configure DATA_PATH, package hashes and sizes, COMMERCE_WEBHOOK_SECRET, ENTITLEMENT_CACHE_HOURS, and RATE_LIMIT_PER_MINUTE as applicable. The complete example is services/licensing-service/.env.example.

!

Secrets must be at least 32 random bytes and stored in a managed secret store. Environment files are for local development only. Persistent SQLite is for controlled single-instance installations — implement the documented repository interface with PostgreSQL before scaling horizontally.

Rate limits

The built-in single-instance limiter defaults to 60 requests per client-route per minute and returns 429 with Retry-After. Production reverse proxies should add global and distributed limits, connection and request-body limits, bot/DDoS controls, and trusted-proxy address handling.

Full operational detail — backup and restore, monitoring and alerting, the incident runbook, and data retention — is in LICENSING_OPERATIONS.md. Commercial terms are templated in COMMERCIAL_ENTITLEMENT_TERMS_TEMPLATE.md.
